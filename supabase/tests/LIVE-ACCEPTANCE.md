# Live Phase 6 acceptance

Double-click `Run-Phase6-Acceptance.cmd` from this folder with Node installed. Supply three dedicated, confirmed QA parent accounts: A and B become parents of family A; C owns family B. Fictional email defaults are examples, not working credentials. Create confirmed QA accounts separately in Supabase before running. Passwords are hidden and passed through the child process standard input only, never files, environment variables, arguments, or logs. Plaintext exists briefly in process memory.

The runner uses the existing public development configuration and refuses any project other than hijtwgugzzpjjkuutyfy. It examines all three parents before creating families and refuses memberships outside families named `QA P6 ...`. New families use `QA P6 A` and `QA P6 B`. Existing tagged QA families can resume. Never supply a real family's parent credentials. The runner queries only its own parent memberships for this safety gate, then uses explicit approved family filters.

`phase6-backend-fixtures.json` stores nonsecret QA family, actor and user IDs. Keep it for resuming. Each run replaces only its own recorded anonymous teen identity; it does not revoke other QA teens, including a phone fixture. Anonymous credentials are never persisted, so each run creates new anonymous identities and revokes the prior backend identity. Fixture Auth rows remain; owner cleanup is separate. Do not delete the manifest while expecting to resume the same teen actors.

Checks cover paired own/cross-family reads, direct role and XP denials, duplicate submission and receipt replay, two separately launched concurrent HTTPS parent approvals, one decision and one nonspendable XP event, revoked old JWT denial, and replacement identity preserving the teen actor. Concurrent client requests demonstrate overlapping launches; they cannot prove the precise server lock-contention timing.

Positive scoring uses an actual provisioned catalogue task with a known deadline later today in Costa Rica. The runner never invents a deadline or writes catalogue rules. After all eligible deadlines pass, that path is reported BLOCKED; rerun during a supported future window. All sessions created by the runner use logout `scope=local` only.

Results are written to `phase6-live-acceptance-results.json` as sanitized check names and statuses. A private outbox check is always UNVERIFIED by ordinary credentials. When the positive path succeeds, `phase6-outbox-owner-audit.sql` contains a separate read-only owner audit scoped to validated fixture UUIDs. Run that manually in the owner SQL editor; expect one pending and one approved event. No owner key belongs in this runner. Exit 2 honestly indicates blocked or unverified coverage; it is not full acceptance.

No live run has been performed merely by installing these files. The runner does mutate dedicated QA data when launched with credentials.

Offline harness verification: `acceptance-offline-adapter.mjs` is a Node preload adapter that intercepts every runner HTTPS call and output-file write. It exercises both populated QA families, request receipt fields, overlapping approval launches, denial checks and replacement history recovery with in-memory fake data. Run Node with `--import ./acceptance-offline-adapter.mjs ./verify-live-acceptance.mjs` from this folder, supplying a JSON array of three dummy email/password objects on standard input. This is not a live backend result and writes no fixture report. Expected runner exit is 2 because the owner outbox audit remains unverified. Use only dummy values with this offline adapter.
