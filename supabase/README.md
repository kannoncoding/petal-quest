Phase 7 (`202610210002_phase7_parent_health.sql`) adds teen-enrolled installations, strictly typed date-only sharing, and parent-requested wipes targeting exactly one installation, Auth identity, actor, family, and enrollment generation. Every installation enrolls independently of journal contents using the generic label “Teen device”; registration never carries dates. The random installation UUID persists outside the vault; rotate the enrollment UUID after identity/family changes or vault deletion, and never reuse a retired generation. Server rows are scoped to installation plus Auth identity. A parent request snapshots the current generation and expires after 30 days; duplicate request IDs preserve that exact snapshot. It never broadcasts to future devices. Parent lists report requested/claimed/done command status; done requires the authenticated device ACK and reveals no empty-vault result or deleted-record count. The first successful claim under the family lock is the authorization instant: later revocation can race an already authorized local wipe. Retry a claimed command after a crash; erase the local vault, ACK using the old generation, then enroll a fresh generation. ACK removes only that generation's shared ranges and reserved alert recipients and returns the same `done` result for empty journals. No alert production/delivery exists until threshold, timing, and text are approved. `list_period_ranges(p_family_id)` returns only installation ID, record ID, start date and nullable end date. Range writes reject future dates, reversed dates, and overlapping periods.

Local review scenarios (prepared, not executed): parent/teen cross-family reads and every mutation fail or return no rows; revoked issuer before claim fails, after claim a retry remains authorized; cross-identity, wrong-installation and old-generation claims/ACKs fail; duplicate requests never retarget after generation rotation; retired generations cannot re-enroll; empty and populated vault ACKs return identical JSON; only ACK removes shared metadata; a replacement teen identity cannot receive old commands; direct table writes and anonymous RPC calls fail. This migration has not been applied to any database and no SQL runtime or acceptance result is claimed.


Migration 003 independently adds high-pain check-ins with a deliberately disabled private policy row: both `include_backdated` and approved generic `push_text` must be set by a privileged owner migration before ingestion queues anything. Numeric pain, symptoms and free text are never accepted. The teen client asserts the confirmed 7–10 threshold through `submit_high_pain_checkin(installation_id, enrollment_generation, local_date, event_id)`. One event per installation/identity/generation/date creates recipient snapshots for then-active parents; repeated edits/retries cannot produce another event. Parent `list_parent_checkins()` returns only generic check-in dates for the current active family/recipient. ACK or generation rotation purges the target's check-in event and queue metadata.

Server-only `claim_high_pain_push(p_limit default 20)` leases up to 100 eligible recipient deliveries for five minutes using SKIP LOCKED; it returns `{deliveries:[{delivery_id,lease_id,recipient_user_id,tokens,push_text}]}`. It rechecks active parent, teen, current installation generation and matching family push registrations. `complete_high_pain_push(p_delivery_id,p_lease_id,p_success)` accepts only the unexpired lease and returns `done` or `stale_lease`; false releases for retry. These two RPCs are granted only to service_role, never to mobile authenticated roles. The worker must keep service credentials private, avoid payload logging, and independently handle duplicate sends after crashes: an FCM send and SQL receipt cannot be one transaction. A revocation or wipe after claim can race an in-flight push. The migration does not configure FCM credentials, send notifications, or claim runtime validation. The independent dates/wipe migration remains usable while this policy is unset.
