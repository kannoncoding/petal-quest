## Client and worker contract

`register_family_device(p_installation_id uuid,p_token text,p_app text,p_request_id uuid)` requires `p_app` (`parent` or `teen`) to match the current authoritative active membership. It returns `status`, `installation_id`, and `request_id`. `unregister_family_device(p_installation_id uuid,p_request_id uuid)` revokes only that authenticated user's installation and returns `status` and `request_id`. Stable request IDs identify exact retries. Each new bind/unbind operation needs a new request ID. Client code must serialize token reconciliation so an earlier token bind cannot overwrite a later token bind.

`list_family_notices(p_limit integer=50,p_before timestamptz=null)` returns `{notices:[...]}` under invoker RLS. The FCM envelope is data-only: `kind=family_update`, `event_id`, `recipient_user_id`, `family_id`, optional `teen_id`/`local_date`, `destination`, and `expires_at_epoch`. Destinations are `review`, `today`, `results`, `rewards`, `routines`. The generic client display text is **Open Petal Quest to see a family update.** No health content, task titles, descriptions, notes, reasons or accounting amounts are included.

The client fetches current membership before displaying a push and again before deep-link navigation. It rejects another account, family, teen actor, expired hint or logged-out session. Offline logout clears local identity and shown notices immediately; failed server revocation must never enable local notification display. The next bind replaces the prior account binding. A network send can race a membership change after the final service authorization, so these client checks remain required.

The worker uses only service-granted `claim_family_event_push`, `authorize_family_event_push`, and `complete_family_event_push`. Each installation has its own lease and receipt; one device's success does not complete a failed sibling. Leases last90 seconds, at most8 attempts use exponential backoff capped at one hour, and notices expire after7 days. Old token receipts cannot deactivate a newer binding. Invalid FCM tokens are deactivated. Unsuccessful notice materialization leaves the committed business outbox intact for reconciliation and cannot roll back XP. The first worker run may recover business facts from the preceding7 days; event identity prevents duplicate notice rows. App refresh recovers missed delivery.

## Source review findings resolved

- Token changes rotate binding identity, preventing an old invalid-token receipt from revoking a newly rotated token.
- Token movement retains the prior installation's durable receipts while removing its token and deactivating its old binding.
- Final authorization checks member, role, teen actor, family, current installation binding, lease and expiry in the same database statement used to return the token.
- Cleanup does not deadletter an active eighth-attempt lease before the sender can finish it.
- Publication validation uses an explicit family allowlist, including rejection of arbitrary session tables in public schemas.
